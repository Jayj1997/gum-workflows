# Gum-Workflows 平台核心设计：组件定义体系与迭代执行引擎

> 状态：设计文档（决策已与维护者逐项确认，见附录 B 决策索引；实施期间任何打破本设计的变更必须先与维护者讨论修订本文档）。
> 定位：MVP（`plans/Workflow Engine MVP：workflow-v1 设计与实现计划.md`）之后的平台化重构设计。**吸收并取代**《Workflow Run History 设计：运行数据留存与查询.md》（该文档尚未实现，其 §5 库文件名与 §7 写入路径按本文档 §8 修订）。
> 三大变化：**四层定义体系**（Node Type / Node Definition / Node Executor / LLM Config 分离，YAML 按名引用、落库 UUID 主键）；**有环迭代执行引擎**（废除无环约束，节点凭新输入版本反复运行，人工在环）；**本地 SQLite 统一库**（定义侧 + 运行历史）。

## 1. 目标与非目标

### 1.1 目标

1. **定义与实例分离**：平台「认识什么 Node」（Node Definition）与「Workflow 里怎么用」（Node Instance）分层，Node Type（agent/automation/human）作为类别层，Node Executor 以版本机制支撑 Node 迭代不影响既有运行。
2. **有环迭代执行**：Workflow 允许成环；节点只关心「输入收集完毕即运行」，上游产出新版本即触发下游重跑；支持「coding agent 循环直至目标完成」与「审批拒绝带意见重做」两类循环。
3. **人工在环（human-in-the-loop）**：human 类节点以前台交互（stdin）承接需求输入与审批决策；运行无显式终态，由用户手动结束。
4. **LLM 配置用户级复用**：providers/models 声明在用户级 `llm.yaml`，跨 Workflow 复用，节点按默认链解析，密钥不落库。
5. **本地 SQLite 统一库**：定义侧（随 run 导入）与运行历史共存于项目本地单库 `.workflow/gum-workflows.db`，可用 `sqlite3` 直接检查。

### 1.2 非目标（本次不做）

- 不做 UI、分布式/服务端数据库、多租户、Secret Management 基建（仅环境变量引用）。
- 不做动态加载外部 Go 代码：Executor = 随二进制编译的 Go 实现 + 内嵌 YAML 声明；用户自定义外挂 Node 属后续「YAML 导入能力」扩展。
- 不做多项目（Workflow 内 `projects` 本期校验恰好 1 个）、不做 resume（挂起后恢复运行）、不做重试/超时/parallelism 等 workflow/v2 字段。
- 不做真实 LLM 网络客户端：`internal/llm` 只含配置结构与解析器；真实 Agent Adapter（含 HTTP 调用）仍属后续版本。
- 不做 `import` 子命令（约束 #5）：定义导入是 `run` 的隐式动作。
- file 类 Artifact 的真实产出/消费（human-input 本期只收文本；`file:ext` 类型语言已预留）。

## 2. 组件总览与引用关系

Go 中不存在继承，组件间关系全部落地为**组合 + 引用**；引用在 YAML 层按 **name**（人类可读），落库层换 **UUID**（`yaml 文件本身不体现 id，仅持久化后体现在数据表里`）。

```text
Node Type Definition（agent / automation / human，全局恰 3 个，种子数据）
        ▲ type: <name>
Node Definition（requirement-analysis 等，inputs/outputs 契约的声明处）
        ▲ node: <name>              ▲ node: <name> + version
Node Instance（workflow.yaml 内）   Node Executor Definition（某定义的一个可执行版本）
        ▲ 汇总                              ▲ Go 实现按 (definition, version) 注册
Workflow ── projects: [Project Definition]
        ── nodes: [Node Instance] ── llm: <provider-name> ──> 用户级 llm.yaml（不落库）
```

| 组件 | 信封 apiVersion / kind | 所在 YAML | 落库表 |
|---|---|---|---|
| Node Type Definition | `nodeTypeDefinition/v1` / `nodeTypeDefinition` | 内嵌种子 | `node_type_definition` |
| Node Definition | `nodeDefinition/v1` / `nodeDefinition` | 内嵌种子 | `node_definition` |
| Node Executor Definition | `nodeExecutor/v1` / `nodeExecutor` | 内嵌种子（每版本一份） | `node_executor` |
| LLM Config（providers/models） | `llm/v1` / `llm` | 用户级 `llm.yaml` | **不落库** |
| Project Definition | （本期无独立信封，内嵌 workflow） | workflow.yaml | `workflow.projects_json` |
| Node Instance | （内嵌 workflow） | workflow.yaml | `node_instance` |
| Workflow | `workflow/v1` / `workflow` | workflow.yaml | `workflow` |

kind 值统一为小写：`workflow` 的 kind 由现 `Workflow` 同步改为小写（未上线，无兼容包袱；CUE 与 loader 同步）。

## 3. 组件定义

### 3.1 Node Type Definition（节点类型定义）

节点按**执行主体**划分的类别层，全局恰好三个，以种子数据内嵌分发，不可由 Workflow 作者增删。

```yaml
apiVersion: nodeTypeDefinition/v1
kind: nodeTypeDefinition
metadata:
  name: agent
  description: 以 AI 执行的节点。执行需要大模型配置（llm.yaml 提供解析）。
requires: [llm]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `metadata.name` | ✓ | `agent` \| `automation` \| `human`，全局唯一 |
| `metadata.description` | ✓ | 类别描述 |
| `requires` |  | 该类节点的共性能力需求，v1 合法值：`llm`、`project`。agent → `[llm]`；automation/human → 空 |

种子数据（`agent` / `automation` / `human`）以三份 YAML 内嵌（§3.8），run 启动时导入 `node_type_definition` 表（幂等 upsert，name 为自然键）。

### 3.2 Node Definition（节点定义）

平台认识的一个节点本体：契约（inputs/outputs）的**唯一声明处**。契约从 Go 代码迁至 YAML（这是本次重构的关键决定：Go 实现不再自带 Schema，为将来用户自定义节点铺路；启动时做声明/实现一致性检查，§6.9）。

```yaml
apiVersion: nodeDefinition/v1
kind: nodeDefinition
metadata:
  name: coding-agent
  description: 在项目 Workspace 中执行编码任务的 agent。
type: agent
requires: [project]
inputs:
  analysis-output: {type: markdown, optional: true}
  architecture:    {type: ArchitectureSpec, optional: true}
  openapi:         {type: OpenAPI, optional: true}
  frontend-sdk:    {type: FrontendSDK, optional: true}
  advise:          {type: markdown, optional: true}   # 声明后方可接收人类意见（§6.6）
outputs:
  source-code: {type: SourceCode}
  openapi:     {type: OpenAPI}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `metadata.name` | ✓ | 全局唯一（如 `coding-agent`），YAML 引用与落库自然键 |
| `metadata.description` | ✓ | 节点职责描述 |
| `type` | ✓ | 引用 Node Type Definition 的 name |
| `requires` |  | 该节点自身的额外资源需求（如 `[project]`）。实例的有效需求 = type.requires ∪ requires |
| `inputs` |  | 端口 → `{type, optional, description}`；`optional: true` 仅 inputs 合法 |
| `outputs` |  | 端口 → `{type, description}` |

校验：`type` ∈ 三值之一；requires 合法值；TypeExpr 语法合法（§4）且其中的语义 Kind 已注册（artifact Registry，含 optional 端口——修复现实现漏检 OptionalInputs 的问题）。

### 3.3 Node Executor Definition（节点执行器定义）

某 Node Definition 的一个可执行版本。**一条数据 = 一份 YAML 声明 + 一个编译进二进制的 Go 实现**，按 `(definition name, version)` 寻址；同一定义多版本并存，使 Node 可迭代而不影响既有运行。

```yaml
apiVersion: nodeExecutor/v1
kind: nodeExecutor
metadata:
  name: coding-agent-v1
  description: coding-agent 首个执行器（Mock 实现）。
node: coding-agent        # 所属 Node Definition（按 name 引用）
version: v1
updates: 首个版本：Mock 编码 agent，写 .mock-agent/task.md 模拟改码。
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `metadata.name` / `description` |  | 展示用 |
| `node` | ✓ | 所属 Node Definition 的 name |
| `version` | ✓ | `v1`、`v2`……，同一定义内唯一 |
| `updates` |  | 该版变更说明 |

Go 侧实现按 `(Definition(), Version())` 注册（§6.9）；内置 Executor 的 YAML 随二进制内嵌（§3.8），run 启动时导入 `node_executor` 表。

### 3.4 LLM Config（用户级 llm.yaml）

agent 节点的大模型配置。**声明在用户级、跨 Workflow 复用、纯运行时不落库**（项目 DB 不沉淀运行者的私人配置；run 启动时把解析结果的名字记入运行记录，§8.3）。

文件位置（查找顺序）：

1. `$XDG_CONFIG_HOME/gum-workflows/llm.yaml`
2. `~/.config/gum-workflows/llm.yaml`

```yaml
apiVersion: llm/v1
kind: llm
providers:
  - name: openai                    # 全文件唯一
    description: 主力模型
    type: openai-compatible         # openai-compatible | anthropic
    url: https://api.openai.com/v1
    apikey: $OPENAI_API_KEY         # 环境变量引用（推荐）；也允许明文
    default: true                   # 全文件至多一个；都不设 → 第一个为默认
    models:
      - name: gpt-4o                # provider 内唯一
        default: true               # provider 内至多一个；都不设 → 第一个为默认
        temperature: 0.2            # 可选，缺省 0.2
        max_tokens: 4096            # 可选
      - name: gpt-4o-mini
  - name: anthropic
    type: anthropic
    url: https://api.anthropic.com
    apikey: $ANTHROPIC_API_KEY
    models:
      - name: claude-sonnet-5
```

校验：provider 名唯一；model 名 provider 内唯一；`default` provider 至多一个、provider 内 default model 至多一个；`type` 二值之一；`url`/`apikey`/`models`（非空）必填；`temperature` 等生成参数挂 model 级。

`apikey` 的 `$VAR` 形式在**加载时**从环境变量解析；明文与 `$VAR` 都允许写在 llm.yaml（该文件在用户目录、不进项目库）；解析后的密钥绝不落库。

**解析链（Node Instance 的 llm/target_model，§3.6）**：

| `llm` | `target_model` | 结果 |
|---|---|---|
| 填 | 填 | 该 provider 的该 model（model 必须属于它，否则报错） |
| 填 | 空 | 该 provider 的默认 model |
| 空 | 填 | **默认 provider** 中找该 model 名（找不到报错，提示补 `llm:`） |
| 空 | 空 | 默认 provider 的默认 model |

### 3.5 Project Definition（项目定义）

被加工的本地代码仓库声明，本期**内嵌于 workflow.yaml**（`projects` 列表），无独立 YAML 信封（将来独立导入时再补信封）。

```yaml
projects:
  - name: order-system
    repository: ./project     # 相对（相对 workflow 文件所在目录）或绝对路径
```

- 字段：`name`（必填）、`repository`（必填，路径存在且为目录）。**无 branch**（本地项目无意义）。
- 本期校验 `projects` **恰好 1 个**；每 run 仍复制一份 Workspace（§6.8）。

### 3.6 Node Instance（节点实例）

Workflow 中对一个 Node Definition 的一次使用。**YAML 形态从简**（用户只填「用哪个 node + 可选的版本/模型 + 输入绑定」），UUID 与解析后的 id 在落库时生成/固定（§8.3）。

```yaml
nodes:
  backend:                     # Node ID：map key，Workflow 内唯一，引用寻址用（不含 "."）
    node: coding-agent         # Node Definition name（原 type: 字段改名）
    executor: v1               # 可选；缺省 = run 启动时发现的最新版本，解析后固定
    llm: openai                # 可选；仅 agent 类节点合法
    target_model: gpt-4o       # 可选；仅 agent 类节点合法
    metadata:                  # 可选，纯展示
      name: 后端实现
      description: 依据需求与架构产出后端源码
    inputs:                    # 语义不变：from 隐式产生 Data Edge
      analysis-output: {from: requirement.analysis-output}
      architecture:    {from: architecture.architecture}
      advise:          {from: review.advise}    # 声明式 advise 回环（普通数据边）
    dependsOn: []              # 可选 Control Edge，语义见 §6.4
    config:                    # 可选，透传给 Executor 的参数
      task: 实现 order-system 后端
```

`llm`/`target_model` 出现在非 agent 类节点 → 校验错误。`inputs` 绑定的端口名必须在该 Node Definition 契约中声明（required 或 optional）。

### 3.7 Workflow

```yaml
apiVersion: workflow/v1
kind: workflow
metadata:
  name: fullstack-development
  version: "1.0"
  description: 全栈开发流水线（含人工审批循环）
projects:
  - {name: order-system, repository: ./project}
nodes:
  requirement: {node: human-input}
  analysis:    {node: requirement-analysis, inputs: {requirement: {from: requirement.requirement}}}

```

- 自然键 `(metadata.name, metadata.version)`，同键重导入 = 覆盖。
- **没有 `llm_configs` 段**：LLM 配置在用户级 llm.yaml（§3.4）。
- Schema 变更点（对现 v1，原地演进、不引入 v2）：`nodes.<id>.type` → `node`；新增 `executor`/`llm`/`target_model`/`metadata`；`project`（单数）→ `projects`（列表）；kind 值小写化。

## 4. 端口类型语言（TypeExpr）

inputs/outputs 端口的类型表达式。语法：

```text
typeExpr := union | single
union    := single ("|" single)+          # 任一成员匹配即通过
single   := atomic | kind | list
list     := "[" typeExpr "]"              # 多值端口
atomic   := "string" | "int" | "bool" | "float" | "markdown"
          | "file" | "file:" ext          # ext := [a-z0-9]+（jpg、pdf…）
kind     := 已注册 Artifact Kind（大写开头，如 RequirementSpec、SourceCode）
```

示例：`string|file:jpg|file:png`、`[markdown]`、`ArchitectureSpec`、`markdown`。

**匹配规则**：兼容 = 生产者类型的每个可能取值都落在消费者类型集合内（consumer ⊇ producer）。具体：原子/Kind 字面相等；list 递归比较成员；union 一侧展开后按成员包含判断。**无隐式子类型**——`markdown` 不自动兼容 `string`，`file:jpg` 不自动兼容 `file`；要宽就显式写 union。理由：可预测性优先，语义 Kind 匹配是内置契约的主流。

分工：CUE 校验 TypeExpr 的**语法形态**（受限字符串 pattern）；Go 语义校验器解析并做**兼容判断**（替换现 Kind 精确相等检查，engine 输出契约检查同步替换）。运行时表示：`string/int/bool/float/markdown` → `Artifact.Data` 存对应 Go 标量；Kind → 现有结构（不变）；`file` 本期仅语言预留。

## 5. 执行语义：迭代引擎

对现引擎的根本性修订：**废除无环约束**。节点唯一的调度关注点是 Ready；环不再是校验错误（§7 环检查降级为提示），运行期由收敛保护兜底（§6.7）。

### 6.1 Ready 与触发规则

```text
Ready(Node) = 所有数据输入都有「已完成轮的产出」（首跑）
              AND 所有 control 前驱都「完成过至少一轮」
重新 Ready(Node) = 任一数据输入出现「未消费的新完成版本」（dirty）
                    OR 任一 control 前驱出现「新的完成轮」（审批节点限「通过轮」，§6.5）
```

- **新输入即重跑**：上游产出新版本 → 数据下游 dirty → 重新入队。上游重跑会级联重跑全下游（含未被拒的分支）——这是迭代模型的既定代价。
- **输入取值**：Node Run 启动时，各输入取生产者**最新已完成轮**的输出（`from` 寻址「当前有效输出」，非某一轮；某轮的具体输出经 node run id / round 寻址，只用于历史查询）。
- **轮次合并**：多个输入版本变化合并为一轮（启动时统一取最新）；运行期间上游又出新版，不中断当前轮，当前轮完成后 dirty 仍在则再跑一轮。
- **节点单并发**：同一节点同时至多一个 Node Run 在跑；重跑请求以 dirty 标记排队，当前轮结束后处理。

### 6.2 状态机

节点级（`Succeeded` 语义 = 本轮完成，**可重入**）：

```text
Pending → Ready → Running → Succeeded
                 ↘ WaitingHuman（human 节点等待输入/决策）→ Running
Running → Failed（结构性 → 运行终止；交互性 → 运行保持，§6.6）
Succeeded → Ready（新输入版本 / control 前驱新完成轮）
Failed    → Ready（advise 重试 / 人类事件级联复活，仅交互性错误）
```

运行级：

```text
Running（常态，全图静止也保持 Running 等待下一轮用户输入——如 Claude Code 空闲不退出）
  → Stopped（用户 Ctrl-C / SIGTERM；stopped_reason=user_interrupt）
  → Failed（结构性错误 fail-fast；收敛保护触发）
```

`Skipped` 枚举保留但本期不产生。状态流转合法性仍集中在 `execution/state.go` 判断，非法流转返回错误。

### 6.3 Node Run 与轮次

一个节点在一次 Workflow 运行内的一次执行 = Node Run，独立 UUID（node run id）+ `round`（第几轮，1 起）。运行侧内存形态：

```go
type NodeExecution struct {
    NodeID       string
    Current      NodeRun            // 调度器视角的当前轮
    History      []NodeRun          // 既往轮，按 Round 排序
    dirty        bool               // 有未消费的新输入版本（未导出）
    machineRuns  int                // 收敛保护计数（自上次人类事件，未导出）
}
type NodeRun struct {
    RunID     string                // UUID，每次执行新分配
    Round     int
    Status    Status
    Inputs    map[string]InputSnapshot   // 绑定声明 + 解析后的引用（含即时 advise，§6.6）
    Outputs   map[string]artifact.ArtifactRef
    Error     string
    ErrorKind string                // "" | structural | interaction
    StartedAt, FinishedAt time.Time
}
```

state.json 布局扩展（§8.4）：`nodes/<node-id>/state.json` 存当前轮 + 历史轮摘要；`nodes/<node-id>/runs/<round>.json` 存每轮明细。

### 6.4 Data Edge 与 Control Edge（迭代语义）

- **Data Edge**（`inputs.from`，隐式）：语义升级为「订阅」——生产者每产出新版本，下游标记 dirty。数据依赖永远不以 dependsOn 表达（不变）。
- **Control Edge**（`dependsOn`，显式）：前驱每出现新的完成轮，后继重新 Ready。典型用例即 human-approval 挂接被审节点：`review.dependsOn: [backend]`，backend 每完成一轮 → review 重新 Ready → 等人审。

### 6.5 approve 门控（审批轮的传播规则）

human-approval 节点的完成轮按 approve 值分两类，**门控传播**：

| | 拒绝轮（approve=false） | 通过轮（approve=true） |
|---|---|---|
| 输出版本更新 | 正常更新最新版本 | 正常更新最新版本 |
| 数据下游（已消费过旧版） | dirty → 重跑（advise 回环即由此驱动） | **不 dirty、不重跑**（通过 =「下游可继续」，不是「输入变了」） |
| 数据下游（从未运行，首跑） | 正常供给 | 正常供给 |
| control 下游（dependsOn 该审批） | 不解禁 | 解禁（重新 Ready） |

由此审批循环零新语法：`backend.inputs.advise: {from: review.advise}` + `review.dependsOn: [backend]`。拒绝 → advise 新版本 → backend 重跑 → backend 新完成轮 → review 重新 Ready → 再审；通过 → 全图静止收敛。

### 6.6 错误二分法与恢复

结构性/交互性错误是运行韧性的核心区分：

| | 结构性（Structural） | 交互性（Interaction） |
|---|---|---|
| 例子 | automation 脚本无法执行、LLM 网络不可达、stdin 关闭 | agent 预期 JSON 返回非 JSON、产出不合格 |
| 本质 | 工作流底层坏了，人工在运行内修不了 | agent 与 AI 交互的质量问题，人类 advise 可救 |
| 节点 | Failed | Failed |
| 运行 | **Failed，进程退出**（fail-fast；在途 Node Run 等待完成不强杀） | **保持 Running**，其余分支照常推进；失败节点下游保持 Pending |
| 恢复 | 修环境/配置后重新 run | advise 重试（下）或入口新一轮需求级联复活（Failed → Ready） |

实现：`Execute` 返回的错误由 Executor 声明类别（`internal/node` 提供 `Structural(err)` / `Interaction(err)` 包装与 `ErrorKindOf(err)`；**缺省按结构性**——automation/human 节点的任何错误默认结构性，agent 的网络错误 Executor 也应标结构性）。

**Advise Retry（即时意见重试）**：交互性错误发生时 CLI 提示「输入 advise 重试（空行跳过）」；非空输入经引擎注入该节点，节点以新 Node Run 重跑。注入优先级：即时 advise > 数据边 advise 最新版本（它是更新的意见）。**仅声明了 `advise` 输入的 agent 节点可被此路径拯救**；未声明者交互性错误等价结构性处理（校验时对「agent 类 definition 未声明 advise 输入」给出提示级 warning）。advise 重试属人类事件，重置收敛保护。

### 6.7 收敛保护（Convergence Guard）

只拦「机器自驱」的连续重跑，不误伤人工驾驶：

- 计数：每节点 `machineRuns`，自上一次**人类事件**（human-input 产出一轮 / 审批做出一次决策 / advise 重试）以来的连续机器触发重跑次数；人类事件发生时全部节点计数清零。
- 触发：节点重跑时 +1，超过阈值（默认 10；Engine Option `WithConvergenceLimit`，**不进 YAML**）→ 该节点 Failed（error=convergence-guard），运行 Failed。
- 静态环在**校验阶段降为提示**：环上无 human 节点 → warning「检测到不含 human 节点的环，可能死循环（收敛保护兜底）」；含 human 环 → 合法迭代路径，不提示。

### 6.8 Artifact 版本与 Workspace

- **Artifact 多版本共存**：同一节点同一输出的多次产出以版本号共存（`Artifact.Version` 由恒 `"1"` 改为「该输出的第 N 次产出」），均不删除；`ArtifactRef` URI 唯一性仍由 Store 保证。
- **Workspace 一次 run 内复用**：多轮重做在同一 Workspace 上累积（增量修码是特性；上轮痕迹是审查依据），不重建、不回滚。Mock coding-agent 在重跑轮把 advise 与 Round 追加写入 `.mock-agent/task.md`，验证「同 workspace、多轮、意见可见」链路。真实的增量适配属真实 Agent Adapter 范畴。

### 6.9 Node/Executor 注册模型（契约单一来源 = YAML）

```go
// internal/node
type Node interface {
    Execute(ctx ExecutionContext, inputs map[string]artifact.ArtifactRef) (map[string]artifact.ArtifactRef, error)
}
type ExecutorFactory interface {
    Definition() string   // Node Definition name
    Version() string      // v1、v2…
    Create(config Config) (Node, error)
}
```

- `InputSchema()/OutputSchema()/Type()` 从 Node 接口移除：契约以 Node Definition YAML 为唯一来源，Engine/校验器从定义 Registry 取。
- `ExecutorRegistry` 按 `(definition, version)` 注册 Factory；`Latest(definition)` 供缺省解析。
- **启动一致性检查**：Go 注册的每个 `(definition, version)` 必须有对应 Executor YAML 声明，内嵌的每个 Executor YAML 必须有对应 Go 实现，Node Definition YAML 必须存在且 type 合法——任一不一致启动即报错（防止声明与实现漂移，接替原「Engine 输出契约检查防 Mock 漂移」的职责；运行期输出检查仍保留，按 YAML 契约执行）。
- `HumanGateway` 接口定义在消费方 `internal/execution`（§7.4），CLI 注入 stdin 实现、测试注入 fake，engine 不碰终端。

## 7. 人工交互（human 节点，前台阻塞模型）

含 human 节点的 run 在到达时**前台阻塞**于终端等待输入（进程活着；关终端/非 TTY 语义见 §7.4）。挂起-恢复式（落盘退出、`approve/resume` 子命令）列为后续演进。

### 7.1 human-input（内置入口节点）

- 契约：无 inputs、无 dependsOn（源节点）；outputs: `requirement: markdown`。
- 运行开始即等待第一轮输入；每轮输入产出新版本 requirement，级联全下游重跑。
- 交互：多行输入，**空行结束本轮**；随后询问 `Continue / Finish`——Continue 进入下一轮等待，Finish 关闭该入口（不再产出；运行继续收敛剩余工作，静止后保持 Running 等待 Ctrl-C）。

### 7.2 human-approval（内置审批节点）

- 契约：无 inputs、**dependsOn 必须非空**（挂接被审节点）；outputs: `approve: bool`、`advise: markdown`。
- 提示前打印本次 run 已产出 artifacts 摘要（名称/Kind/版本/URI，取最新轮），审批人有据可查；历史上已收到的 advise 一并列出。
- 交互：`Approve / Reject (with advise)? [A/r]`——回车默认 Approve；`r` 后同行（或下一行）输入 advise（拒绝时建议填写，不强制）。

### 7.3 交互性错误的 advise retry

见 §6.6。CLI：`✗ backend 失败（交互性）：<错误摘要>。可输入 advise 重试（空行跳过）：`——空行=不重试，节点保持 Failed、运行继续等待其他事件。

### 7.4 HumanGateway 与非 TTY

```go
// internal/execution（消费方定义）
type HumanGateway interface {
    RequestRound(ctx context.Context, req RoundRequest) (RoundResponse, error)
}
// RoundRequest：节点信息（NodeID/Definition）、请求类别（input|approval|advise-retry）、
//               展示上下文（已产出 artifacts 摘要、历史 advise）
// RoundResponse：input → {Content string, Finished bool}
//                approval → {Approved bool, Advise string}
//                advise-retry → {Advise string, Skip bool}
```

非 TTY（stdin 非控制台）运行含 human 节点的 workflow → **启动即报错**（提示需交互终端）。取消（Ctrl-C）：WaitingHuman → Failed（节点级），运行记 Stopped。

## 8. 持久化（SQLite 统一库）

### 8.1 库与文件系统分工

```text
.workflow/
├── gum-workflows.db         # SQLite 统一库（定义侧 + 运行历史索引）
└── executions/<execution-id>/   # 运行数据主体（不变原则：DB 存引用不存本体）
    ├── workflow.yaml / state.json / nodes/<id>/{state.json, runs/<round>.json}
    ├── artifacts/<n>.json   # Artifact 本体（多版本共存）
    └── workspace/project/
```

驱动 `modernc.org/sqlite`（纯 Go 无 CGO）、WAL、busy_timeout、`PRAGMA user_version` 顺序迁移——沿用 run-history 设计 §9，此处不重复。

### 8.2 导入与解析时机（run 是唯一写入口）

`workflow run` 启动那一刻为**唯一解析点**，顺序：

1. 打开/迁移库；导入内嵌种子（node types / definitions / executors，幂等 upsert）。
2. upsert 本 workflow（自然键 name+version，覆盖式）及其 projects、node instances。
3. 逐节点解析并**固定**：executor 缺省 → 当时能发现的最新版本（DB 与二进制中该 definition 的最大版本号，记入 `node_instance.node_executor_id`，**非持续 latest**）；llm/model 缺省 → 按默认链（§3.4）解析为名字字符串记入行。
4. 执行期绝不漂移：本 run 与其历史查询均以固定结果为准；下次 run 重新解析（可能已是新版本）。

`workflow validate` **纯只读零副作用**：同样做语义与解析检查（含 llm.yaml 引用），但不建库不写库。`workflow history` 只读。

### 8.3 表结构（DDL）

定义侧（UUID 主键；YAML 不含 id，导入时生成）：

```sql
CREATE TABLE node_type_definition (
  id            TEXT PRIMARY KEY,          -- UUID
  name          TEXT NOT NULL UNIQUE,      -- agent|automation|human
  description   TEXT NOT NULL DEFAULT '',
  requires_json TEXT NOT NULL DEFAULT '[]',
  created_at    TEXT NOT NULL
);

CREATE TABLE node_definition (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL UNIQUE,
  description   TEXT NOT NULL DEFAULT '',
  type          TEXT NOT NULL REFERENCES node_type_definition(name),
  requires_json TEXT NOT NULL DEFAULT '[]',
  inputs_json   TEXT NOT NULL DEFAULT '{}',
  outputs_json  TEXT NOT NULL DEFAULT '{}',
  created_at    TEXT NOT NULL
);

CREATE TABLE node_executor (
  id                  TEXT PRIMARY KEY,
  node_definition_id  TEXT NOT NULL REFERENCES node_definition(id) ON DELETE CASCADE,
  version             TEXT NOT NULL,       -- v1、v2…
  name                TEXT NOT NULL DEFAULT '',
  description         TEXT NOT NULL DEFAULT '',
  updates             TEXT NOT NULL DEFAULT '',
  created_at          TEXT NOT NULL,
  UNIQUE (node_definition_id, version)
);

CREATE TABLE workflow (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  version       TEXT NOT NULL DEFAULT '',
  description   TEXT NOT NULL DEFAULT '',
  projects_json TEXT NOT NULL DEFAULT '[]',
  created_at    TEXT NOT NULL,
  UNIQUE (name, version)
);

CREATE TABLE node_instance (
  id                  TEXT PRIMARY KEY,
  workflow_id         TEXT NOT NULL REFERENCES workflow(id) ON DELETE CASCADE,
  node_id             TEXT NOT NULL,       -- Workflow 内 Node ID（map key）
  node_definition_id  TEXT NOT NULL REFERENCES node_definition(id),
  node_executor_id    TEXT NOT NULL REFERENCES node_executor(id),  -- 解析后固定
  display_name        TEXT NOT NULL DEFAULT '',
  description         TEXT NOT NULL DEFAULT '',
  llm_provider        TEXT NOT NULL DEFAULT '',  -- 解析后名字（llm.yaml 不落库）
  llm_model           TEXT NOT NULL DEFAULT '',
  inputs_json         TEXT NOT NULL DEFAULT '{}',
  depends_on_json     TEXT NOT NULL DEFAULT '[]',
  config_json         TEXT NOT NULL DEFAULT '{}',
  UNIQUE (workflow_id, node_id)
);
```

运行侧（吸收 run-history 设计，按 node-run 粒度改写；`workflow_run_history` 增加 `stopped_reason`，status 集合改 `Running|Stopped|Failed`）：

```sql
CREATE TABLE workflow_run_history (
  id              TEXT PRIMARY KEY,        -- UUID（run id）
  workflow_name   TEXT NOT NULL,
  workflow_version TEXT NOT NULL DEFAULT '',
  status          TEXT NOT NULL,           -- Running | Stopped | Failed
  workflow_file   TEXT NOT NULL DEFAULT '',
  execution_id    TEXT NOT NULL,           -- 磁盘目录名 execution-000001（保持不变）
  error           TEXT NOT NULL DEFAULT '',
  stopped_reason  TEXT NOT NULL DEFAULT '',  -- user_interrupt | convergence-guard | ''
  started_at      TEXT NOT NULL,
  finished_at     TEXT
);
CREATE INDEX idx_run_history_started_at ON workflow_run_history (started_at DESC);
CREATE INDEX idx_run_history_workflow   ON workflow_run_history (workflow_name);

CREATE TABLE workflow_node_run_history (
  id              TEXT PRIMARY KEY,        -- node run UUID
  run_id          TEXT NOT NULL REFERENCES workflow_run_history(id) ON DELETE CASCADE,
  node_id         TEXT NOT NULL,
  node_definition TEXT NOT NULL,           -- 运行快照（name）
  node_executor   TEXT NOT NULL,           -- 运行快照（version）
  round           INTEGER NOT NULL,
  status          TEXT NOT NULL,           -- Pending|Ready|Running|WaitingHuman|Succeeded|Failed|Stopped
  error           TEXT NOT NULL DEFAULT '',
  error_kind      TEXT NOT NULL DEFAULT '',  -- structural | interaction | ''
  inputs_json     TEXT NOT NULL DEFAULT '{}',
  outputs_json    TEXT NOT NULL DEFAULT '{}',
  started_at      TEXT,
  finished_at     TEXT,
  UNIQUE (run_id, node_id, round)
);
CREATE INDEX idx_node_run_history_run ON workflow_node_run_history (run_id);
```

`inputs_json`/`outputs_json` 形态沿用 run-history 设计 §5.3（`ArtifactRef` 序列化；即时 advise 以特殊 from 标记 `#advise-retry`）。运行开始即为全部节点建 Pending 行的原则保留；一轮一行，历史轮次天然留存（「这轮为什么被拒、上轮 advise 是什么」可查）。

### 8.4 state.json 扩展

运行级 `state.json` 增 `run_id/stopped_reason/started_at/finished_at/workflow_file`；节点级 `nodes/<id>/state.json` = 当前轮 + 历史轮摘要；每轮明细 `nodes/<id>/runs/<round>.json`。写入时机沿用「每个状态变化后快照」（persist 即快照，Record 同点）；记录失败不使运行失败（可观测性原则不变）。

## 14. 测试与验收问题

单测/集成沿用 DEVELOPMENT.md §6（表驱动、t.TempDir、禁网络、禁 $HOME——llm.yaml 测试经临时 `XDG_CONFIG_HOME` 注入）。关键新用例：

1. 审批循环收敛：reject(advise) → 重跑 → approve → 全图静止（无多余轮次）。
2. 机器环死循环：无 human 环第 11 轮被收敛保护掐断（error=convergence-guard）。
3. approve 门控：通过轮不触发已运行下游重跑；首跑正常供给。
4. 交互性错误：节点 Failed 运行 Running；advise 重试复活；未声明 advise 输入的 agent 交互性错误等价结构性。
5. 结构性错误：运行 Failed 进程退出，在途轮完成不强杀。
6. 多轮需求：entry 第二轮输入级联全下游重跑；workspace 累积（task.md 追加）。
7. executor 固定：run 中途注册新版本不影响本 run。
8. Stopped：Ctrl-C 后 run 行 status=Stopped、stopped_reason=user_interrupt。

验收问题（设计目标即验收）：
- 「需求是什么时候给的、审了三轮各说了什么？」——`workflow history <run-id> review` 各轮次 advise 一屏可查。

## 附录 A：完整 workflow.yaml 示例（P8 demo 形态）

```yaml
apiVersion: workflow/v1
kind: workflow
metadata:
  name: fullstack-development
  version: "1.0"
  description: 全栈开发流水线：人工需求入口 → 分析/架构/编码 → 人工审批循环
projects:
  - name: order-system
    repository: ./project
nodes:
  requirement:
    node: human-input
  analysis:
    node: requirement-analysis
    inputs:
      requirement: {from: requirement.requirement}
  architecture:
    node: architecture-design
    inputs:
      analysis-output: {from: analysis.analysis-output}
  backend:
    node: coding-agent
    llm: openai
    target_model: gpt-4o
    config:
      task: 实现 order-system 后端：依据需求与架构产出源码与 OpenAPI 文档
    inputs:
      analysis-output: {from: analysis.analysis-output}
      architecture:    {from: architecture.architecture}
      advise:          {from: review.advise}
  review:
    node: human-approval
    dependsOn: [backend]
  openapi:
    node: openapi-generator
    inputs:
      openapi: {from: backend.openapi}
  frontend:
    node: coding-agent
    config:
      task: 实现 order-system 前端：消费 OpenAPI 与 Frontend SDK
    inputs:
      analysis-output: {from: analysis.analysis-output}
      openapi:         {from: backend.openapi}
      frontend-sdk:    {from: openapi.frontend-sdk}
      advise:          {from: review.advise}
```

运行形态：requirement 等待输入 → 全链推进 → review 等待审批；reject(advise「布局太挤」) → backend/frontend 带 advise 重跑 → review 再审；approve → 全图静止，保持 Running 等待下一轮需求或 Ctrl-C（Stopped）。

§4

TypeExpr：端口类型语言

契约端口的类型表达式：原子类型、语义 Kind、union、list 自由组合；匹配规则是「消费者类型集合 ⊇ 生产者」，无隐式子类型。

# 语法
typeExpr := union | single
union    := single ("|" single)+        # 任一成员命中即通过
single   := atomic | kind | list
list     := "[" typeExpr "]"            # 多值端口
atomic   := string | int | bool | float | markdown
          | file | file:ext             # file 本期语言预留

# 示例
requirements: "string|file:jpg|file:png|file:pdf"   # union
test-reports: "[markdown]"                       # list
architecture: ArchitectureSpec                        # 语义 Kind

CUE 校验语法形态（受限 pattern），Go 语义校验器做兼容判断，替换现有 Kind 精确相等检查；顺手修复 OptionalInputs 漏检。

§5–6

迭代引擎：废除无环，新输入即重跑

节点唯一的调度关注点是 Ready：输入收集完毕即运行。上游产出新版本，下游标 dirty 重新入队；级联重跑是模型的既定代价，机器自驱死循环由收敛保护兜底。

Ready(Node)      = 所有数据输入有「已完成轮的产出」 AND control 前驱完成过至少一轮
重新 Ready(Node) = 任一数据输入出现「未消费的新完成版本」(dirty)
                   OR 任一 control 前驱出现新的完成轮（审批节点限「通过轮」）

输入取值         = 生产者最新已完成轮的输出（from 寻址「当前有效输出」）
轮次合并         = 多个输入版本变化合并为一轮；运行中上游再出新版不打断当前轮
节点单并发       = 同一节点至多一个 Node Run 在跑，重跑请求以 dirty 排队

可重入状态机

节点级：  Pending -> Ready -> Running -> Succeeded（本轮完成，可重入：新输入 -> Ready）
                        ↓                        ↘ WaitingHuman（human 节点等输入/决策）-> Running
                                                 ↘ Failed（结构性->运行终止；交互性->运行保持）

运行级：  Running（常态；全图静止也保持 Running，等待下一轮用户输入）
            -> Stopped（Ctrl-C / SIGTERM，stopped_reason=user_interrupt）
            -> Failed（结构性错误 fail-fast；收敛保护触发）

approve 门控：拒绝催更，通过不催更

拒绝轮 approve=false通过轮 approve=true
advise / approve 输出版本正常更新正常更新
数据下游（已消费旧版）dirty -> 重跑不 dirty、不重跑
数据下游（从未运行）正常供给正常供给
control 下游不解禁解禁（重新 Ready）

审批循环零新语法：backend.inputs.advise: {from: review.advise} ＋ review.dependsOn: [backend]。拒绝 -> advise 新版本 -> backend 重跑 -> review 再审；通过 -> 全图静止收敛。

错误二分法与恢复

结构性 Structural

  • 例：automation 跑不起来、LLM 网络不可达、stdin 关闭
  • 本质：工作流底层坏了，人工在运行内修不了
  • 运行：Failed，进程退出（fail-fast）
  • 恢复：修环境/配置后重新 run

交互性 Interaction

  • 例：agent 预期 JSON 返回非 JSON、产出不合格
  • 本质：AI 交互质量问题，人类 advise 可救
  • 运行：节点 Failed，运行保持 Running
  • 恢复：advise 重试（需节点声明 advise 输入）或新一轮需求级联复活

收敛保护：只拦机器自驱

每节点计数「自上一次人类事件（新一轮需求 / 审批决策 / advise 重试）以来的连续机器触发重跑」；超过阈值（默认 10，Engine Option，不进 YAML）-> 节点 Failed，运行 Failed。人类事件清零全部计数--人工驾驶的长会话永不被误伤。静态可判的纯配置环在校验阶段降为 warning。

Node Run 与版本语义

每次执行 = Node Run（UUID + round）。inputs.from 总取最新已完成轮；某轮具体输出经 node run id / round 寻址（仅历史查询）。同一输出多版本 artifact 共存不删；Workspace 一次 run 内复用，多轮重做累积（增量修码是特性，上轮痕迹是审查依据）。

§7

人工在环：一次会话的形态

human 节点前台阻塞于终端（非 TTY 启动即报错）；运行像 Claude Code 一样活着--空闲不退出，等待下一轮输入，Ctrl-C 才记 Stopped。

human-input 需求第 1 轮
用户在终端输入需求，空行结束本轮 -> requirement v1 -> 全链级联推进
agent analysis -> architecture -> backend
各节点首跑：分析、架构、编码（executor 取 run 启动时固定的最新版）
human-approval review 等待审批
打印已产出 artifacts 摘要 -> r 请把登录页信息密度降低 -> 拒绝，advise v1
agent backend / frontend 带 advise 重跑
advise 新版本 -> dirty -> 重跑（同一 Workspace，task.md 追加轮次痕迹）-> review 重新 Ready
human-approval 通过
回车默认 Approve -> 通过轮不催更下游 -> 全图静止，运行保持 Running
下一轮需求 或 Ctrl-C
入口节点继续等待；用户结束 -> Stopped（stopped_reason=user_interrupt），各轮次 advise 全程可查
§8

持久化：一个 SQLite，两种身份

项目本地 .workflow/gum-workflows.db 同时承载定义侧（随 run 隐式导入）与运行历史索引；文件系统仍是运行数据主体，DB 存引用不存本体，删库可重建。

定义侧五表

node_type_definitionagent / automation / human 种子三行
node_definition契约 JSON（inputs/outputs TypeExpr）
node_executorUNIQUE(definition, version)
workflow自然键 (name, version)，重导入覆盖
node_instance解析后固定 executor id + llm 名字

运行侧两表（node-run 粒度）

workflow_run_historystatus: Running|Stopped|Failed + stopped_reason
workflow_node_run_historyUNIQUE(run_id, node_id, round)，一轮一行

apikey 不落库llm.yaml 写 $VAR 引用，加载时从环境变量解析
validate 零副作用同样做解析检查，但不建库不写库；run 是唯一写入口
